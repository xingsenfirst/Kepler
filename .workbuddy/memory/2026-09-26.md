## 关键教训：bash `set -Eeuo pipefail` 的短路陷阱（用户实测报「第 455 行意外失败」）

- `apply_env_overrides()` 原本以 `[[ -n "$ENV_STAGING" ]] && STAGING="$ENV_STAGING"` 结尾：环境变量没设置时该语句返回 1 → 函数返回 1 → 顶层调用被 ERR trap 当成失败，脚本在**全新机器上必挂**。
- 修法：改成 `if ...; then ...; fi` 并显式 `return 0`；`load_state` / `save_state` 也补 `return 0`；谓词函数 `is_ip_addr` / `is_valid_domain` / `confirm_continue` 改为显式 `return 0/1`。
- 通用规则：**函数最后一条语句不要留条件表达式**；护栏已固化（扫描每个函数最后一条有效语句，排除 if/while 包裹与 `|| true`/`|| return 0`/`|| die` 兜底）。

## 关键教训 2：`pipefail` + 命令替换里的管道（用户实测报「[9/10] 健康检查 第 2075 行意外失败」）

- `diagnose_service()` 里 `who="$(ss -ltnp | grep ":${APP_PORT}\b" | head -n1)"`：端口没人监听时 grep 返回 1 → pipefail 让整条赋值失败 → ERR trap 触发。**讽刺的是这条只在服务没起来时才会走到**，等于把最需要诊断输出的地方变成了脚本自杀点。
- 修法：命令替换里凡是带管道的，末尾一律 `|| true`（或 `|| echo ''`）。顺带排查并补了 8 处同类风险点：端口占用 `owner=`、`APP_VERSION=`、`nginx -v | grep -o`、`nginx -v | sed`、`certbot --version | head`、DNS 查询 `getent`/`dig`/`nslookup`、日志 `grep -viE ... | tail -n 12`、`node -v | sed`（4 处）。
- 通用规则：`grep`/`head -n1` 这类「查不到就返回 1」的命令出现在 `$(...)` 里时，必须显式兜底。护栏已固化（扫描所有含管道的命令替换，要求有 `|| true` / `|| echo` / `|| :`；忽略 `||` 作为布尔或的误报）。

## deploy.sh 自审（第二轮：不看报告，自己找问题）

发现的 8 处问题与修复：

1. **`kepler <编号>` 完全不可用**：包装脚本只在**无参**时补 `--manage`，`kepler 2` 把裸 `2` 传给 parse_args → `die "未知参数：2"`。修法：parse_args 增加 `[0-9])` 分支设 `MANAGE=1; MANAGE_ACTION="$1"`，main 改为按 `MANAGE_ACTION` 分发（不再靠位置参数个数猜，那样 `--manage 2` 会 dispatch 到 `--manage`）。
2. **`kepler 1` 重装必然自锁失败**：`exec` **不触发 EXIT trap** → 锁文件留在磁盘 → 新进程 detect_env 的 noclobber 写入失败 → 判「另一个部署进程正在运行」。实测确认（探针 P3/P4）。修法：抽出 `reinstall_now()`，`trap - EXIT` + `exec env KEPLER_LOCK_HELD="$LOCK_FILE" bash "$target" --reinstall`，detect_env 识别该环境变量把锁**交接**给新进程（保持单实例保护不断档）。菜单与命令行两条路径统一走它。
3. **取值型参数缺值 → 「脚本在第 431 行意外失败」**：`X="${2:-}"; shift 2` 在只给选项时 `shift 2` 越界返回 1 → ERR trap。实测复现。修法：13 个取值型选项合并成一个分支，先 `[[ $# -lt 2 || -z "${2-}" ]]` 校验再取值。
4. **可选依赖降级路径是断的**：`pkg_install_opt` 里 `on_pkg_failure ... 1` 是裸调用，返回 1 直接触发 ERR trap，调用点的 `|| true` 来不及生效 —— 设计成降级，实际中断部署。修法：`|| true`。探针 B 实证了这个语义。
5. **管理入口不校验部署状态**：没 state 时「改端口」会拿内置默认值去写 `.env`、写 `/etc/kepler/deploy.conf`、重启不存在的服务。修法：MANAGE 分支先判 `STATE_LOADED`，未部署就 die_with_hint 指路。
6. **卸载白名单误伤**：`case` 的 `/home/*`、`/root/*` 通配会**跨 `/` 匹配**，把 `/home/deploy/kepler` 正常安装目录也拦掉，卸载永远失败。修法：精确系统目录 + `^/(home|Users)/[^/]+/?$`（家目录本身）+ `/(Desktop|Downloads|Documents)(/|$)` 组件匹配。
7. **删除 CWD 隐患**：`install_app` 会 `cd "$INSTALL_DIR"`，卸载删掉它之后相对路径全失效 → 删除前 `cd /`。
8. **端口建议值非法**：`$(rerun_cmd --port $((APP_PORT + 1)))` 在 65535 时给出 65536。修法：新增 `next_port()`（避开对外端口与 3443/8443，超界回落）。另把 `usage()` 的 `sed -n '2,60p'` 换成「打印到第一个非注释行为止」，避免头注释一改行数就截断帮助。

护栏：`tests/deploy-script.test.js` 5 → **10 条**，新增 5 条（参数缺值的人话错误 + 缺值静态禁用、kepler 编号分发、重装锁交接、可选依赖降级、卸载白名单）。**4 处修复都做了反向变异验证**，确认护栏会真的变红。

### 关键教训 3：探针 harness 自己不靠谱，结论会全错

- **`( ... ) || echo "被杀了"` 会关闭子 shell 内的 errexit**：第一版探针用这个写法验证 `set -e`，全部报「存活」（假阴性）。正确做法是把被测代码放进 `bash -c` 子进程，外层读退出码。
- **同一个 shell 里重复 `source` 带 `readonly` 常量的脚本会失败**：`source deploy.sh` 两次 → `SCRIPT_NAME: readonly variable` → `source` 返回非 0，被 `set -e` 放大成「整段验证脚本崩掉」，于是所有判定都成了「拒绝」（假阳性）。正确做法：只 source 一次，被测函数放进 `( ... )` 子 shell 取返回码。
- **harness 必须显式 `set +e`**：`source` 会把脚本的 `set -Eeuo pipefail` 带进验证 shell，之后任何返回非 0 的语句都会杀掉 harness 自己。
- 探针要覆盖**正反两面**（该拒绝的、该放行的都测），否则「全都拒绝」这种坏实现也会全绿。

### 关键教训 4：Windows 上用 Python 还原文件会把 LF 变成 CRLF

- 变异验证脚本用 Python 的 `Path.write_text(text)` 备份/还原 `deploy.sh`：Windows 下默认 `newline=None` 会把 `\n` **翻译成 `\r\n`**。更坑的是 `read_text()` 读回时又做通用换行转换，所以 `content == original` 断言**照样通过**，文件却已经全文 CRLF（2741 行全变）。
- 后果：3 条静态护栏假红（`/(\|\| die )$/` 这类带 `$` 锚点的正则匹配不到行尾、`indexOf('\nNODE\n')` 找不到 heredoc）。表现为「刚修好的东西又挂了」，极易误判成自己的修复有错。
- 规避：二进制/`latin1` 读写 + 显式 `\n`，或 `open(..., newline='')`；**改完文件后做一次 `\r` 计数自检**（`node -e "统计 CRLF"` 一行即可）。
